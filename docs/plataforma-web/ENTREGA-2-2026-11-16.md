## 5 · Modelo

### La discrepancia 667.727 / 567.634 — resuelta leyendo el código

**Incluye otras federaciones; no son filas duplicadas.** La consulta de `eval_modelos.py` (líneas
137-153) no filtra federación: `where s.anio_inicio >= 2019 and m.goles_local is not null and
m.goles_visitante is not null`. Entrena y valida con todas las del canónico. `04-modelo.py`, el que
publica, hace lo mismo (usa `fed_id` como variable). Los `join` son uno a uno por partido, así que no
multiplican filas. El 0,9377 es de toda España, no de Castilla y León.

La consulta que lo demuestra (bloqueada: necesita la base):

```sql
select f.codigo,
       count(*) filter (where s.etiqueta <= '2023-24')               as entrenamiento,
       count(*) filter (where s.etiqueta in ('2024-25', '2025-26'))  as validacion
  from core.match m
  join core.phase_group pg on pg.id = m.phase_group_id
  join core.competition_edition ce on ce.id = pg.competition_edition_id
  join core.season s on s.id = ce.season_id
  join core.federation f on f.id = ce.federation_id
 where s.anio_inicio >= 2019 and m.goles_local is not null and m.goles_visitante is not null
 group by rollup (f.codigo)
 order by validacion desc;
```

**Aceptación:** la fila de totales da 354.964 y 667.727; la de `castilla-leon` da su parte. Y para
descartar duplicados: `select count(*), count(distinct m.id)` con los mismos `join` y `where` deben
coincidir.

He añadido a `eval_modelos.py` el desglose `por_federacion` (log-loss, Brier y acierto de cada modelo
por federación, con al menos 500 partidos de validación) y `partidos_por_federacion`. No cambia el
entrenamiento ni el modelo. La próxima vez que se ejecute, `evaluacion.json` traerá el número de
Castilla y León.
